Bookkr System Map

How the three Bookkr apps, the chat pipeline and the outside services fit together, and how the Friction Finder should use that map to sort each friction into one of three buckets and send it to the right fix: an engineering ticket, a prompt change, RAG examples or fine-tuning data.

Source: bookkr-combined-uat.zip · docs/architecture/*.md · bookkrapp/src/modules · prisma/schema.prisma

The three buckets

Sort every friction item by what the user ran into. Then a second question, which component made the first wrong decision, picks the fix. Only items where an LLM made the first wrong decision belong in the RAG or fine-tuning dataset.

Technical

The system broke

  • Provider error or timeout (SerpAPI, Tripjack, gateway)
  • LLM call failed, timed out or returned bad JSON
  • Payment failed, fare expired, price changed
  • Slow turn, crash, 5xx
  • Phone never got the event, or an old build drew a stub
Fix: engineering ticket. Never training data.
Intent

Bookkr misread the user

  • User had to repeat a value they already gave
  • Wrong city, date, party, trip type
  • Turn sent to the wrong flow
  • Preference dropped or not applied
  • Asked for something it already had
Fix: RAG or fine-tuning if the LLM got it wrong; code fix if a rule got it wrong.
Agent suggestion

Understood, but offered something poor

  • Results ranked against the stated preference
  • Unrealistic or repetitive trip plan
  • Wrong or ungrounded answer to a travel question
  • Irrelevant reply chips, odd airport or date options
  • Asked for something Bookkr does not do
Fix: prompt or RAG for the LLM that wrote it; ranking or product change otherwise.

LLM step: data can fix it Fixed rule: code fix Outside service: technical

Two things in this pipeline that change how we sort

Many "the bot misunderstood me" moments are decided by code, not by the LLM. After extraction, fixed rules move past dates forward, decide whether a window is exact, detect mixed round trips, pick airports and decide whether to ask or search. If the LLM's output was right and one of these rules changed it, putting that chat into the RAG file teaches the model nothing and adds noise. The judge has to compare three things: what the user said, what the extractor returned (ExtractedIntent.parameters), and what the search actually ran with (FlightSearchRequest, HotelSearchRequest).

The fine-tuned extractor and the RAG file pull in different directions. When the LoRA model serves a turn, it gets the short instruction it was trained on, not the 9k production prompt. Retrieved few-shot examples pasted into that prompt are outside its training format. So the fix for a LoRA miss is new training rows. The fix for a gpt-4.1-mini miss is RAG. LlmCallLog.model shows which model served the turn.

Every LLM task in Bookkr

Each task reads its own GPT_MODEL_<TASK> setting and falls back to GPT_MODEL (gpt-4.1-mini-2025-04-14). Each call is logged to LlmCallLog with its task, model, latency, success and error. That table is how the Friction Finder ties a bad turn to the LLM that caused it.

ChooseWhenWhy
RAG / few-shotOne-off or long-tail phrasing: Hinglish, slang, city nicknames, an odd date form. Under about 20 examples of the pattern. The served model is gpt-4.1-mini.Ships the same day, can be undone, and each example can be traced to a reviewed chat.
Fine-tuningThe same lesson keeps failing the eval with RAG in place. Or the miss is structural: keys lost (the LoRA canonicaliser logs intent.qwen_lora.repaired), state not kept across turns, broken JSON. Or the served model is the LoRA.Teaches the contract itself. Costs a training run (about $10–20 of GPU) and has to pass the ship gates in docs/operations/finetuning.md.
Prompt changeThe lesson is a rule, such as "at most two chips, no money" or "say cabs are coming soon".A rule written once beats twenty examples that imply it.
EngineeringTechnical bucket, or a fixed rule made the first wrong decision.The LLM was right. Training on it would teach the model the wrong thing.

What changes in the Friction Finder

  1. Add a top-level bucket (technical, intent, agent_suggestion) and an owner (the LLM task, the rule or the service that made the first wrong decision) to every item, in the rules, the judge schema and the review page.
  2. Move dead_end and llm_failure out of the intent types into technical sub-types: provider, llm_call, payment_booking, latency, client_delivery, app_error.
  3. Add suggestion sub-types: ranking, plan_quality, answer_quality, chips, airport_or_date_options, product_gap.
  4. Sync AnalyticsEvent (masked, booking, payment, search-result, chip and filter events only) and use LlmCallLog.model and latency.
  5. Give the judge the three-way comparison for each flagged turn: user words, extractor output, search params.
  6. Split the export. Intent items owned by an LLM go to the RAG file, or to the fine-tune queue if the LoRA served them. Suggestion items owned by an LLM go to a separate response-quality file. Everything else goes to an engineering list with the chat link.
  7. Add a bucket filter and per-bucket counts on the Friction page, so technical items don't hide inside the intent queue.
